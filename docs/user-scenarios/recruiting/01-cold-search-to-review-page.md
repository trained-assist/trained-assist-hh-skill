# Recruiting — холодный поиск до страницы ревью

**Домен:** HR / рекрутинг (HeadHunter)
**Класс:** mandatory (в гейте `scripts/staging/suites.json`)
**Тулы:** `hh_list_vacancies`, `hh_proactive_search`, `hh_proactive_view`
**Охват:** от «прогрей базу» до устойчивой страницы ревью, переживающей рестарт
провайдера, плюс честная ошибка доступа и восстановление.

---

## Контекст (начальный state)

- Профиль `fixture` с подключённым HH (в sandbox — токен в `AGENT_TOKENS_DIR`).
- Активная вакансия сохранена в context-store (`contexts/hh/active_vacancy.json`).
- ATS-конфиг вакансии сохранён (`contexts/hh/ats_config:100.json`).
- Резюме доступны через API HH (`GET /resumes`); контакты не открываются.

---

## Сценарий

### Шаг 1 — Список вакансий

```
User: какие у меня вакансии?
```

**Ожидаем:** бот вызывает `hh_list_vacancies`, возвращает открытые вакансии с
полем `manager` (ответственный рекрутёр).

**Validation:**
- `tools/list` содержит `hh_proactive_search`.
- `hh_list_vacancies` → `total=1`, `vacancies[0].manager = "Тестовый рекрутер"`.
- все запросы к HH — `GET`.

**Статус:** ✅ mandatory

---

### Шаг 2 — Холодный поиск (`hh_proactive_search`)

```
User: прогрей базу по активной вакансии
```

**Ожидаем:** один вызов делает полный цикл: генерирует поисковые фразы (LLM),
ищет резюме, скорит кандидатов (LLM), сохраняет снапшот и отдаёт URL страницы
ревью.

**Validation:**
- `hh_proactive_search` → `ok=true`, `count=2`, `url` содержит `vacancy_id=100`.
- LLM вызван ровно 3 раза: генерация фраз + 2 оценки кандидатов; первый промпт
  содержит название вакансии.
- HH `GET /resumes` вызван с повторяющимися query-параметрами (`area`, `text`),
  без платных контактов.
- снапшот сохранён в durable-хранилище (`AGENT_DATA_DIR/hh/<user>/proactive`).

**Статус:** ✅ mandatory

---

### Шаг 3 — Реальная HTML-страница ревью

**Ожидаем:** по `url` отдаётся настоящий HTML со всеми кандидатами, скорами и
ссылками на резюме; фильтры по имени работают.

**Validation:**
- `GET url` → `200`, тело содержит оценки кандидатов и ссылки `hh.ru/resume/...`.
- (браузерный вариант) Chromium: 2 карточки, фильтр по имени сужает список,
  `reload` сохраняет фильтр и кандидатов.

**Статус:** ✅ mandatory

---

### Шаг 4 — Recall после смерти провайдера

**Ожидаем:** `hh_proactive_view` возвращает тот же снапшот после рестарта
MCP-процесса, не повторяя поиск в HH.

**Validation:**
- после `restart()` `hh_proactive_view` → `url` и `count` совпадают.
- число запросов к `/resumes` не увеличилось (recall не переспрашивает HH).

**Статус:** ✅ mandatory

---

### Шаг 5 — Отказ доступа и восстановление

**Ожидаем:** если HH отвечает `403`, поиск честно сообщает об ошибке (не «0
результатов»); после устранения причины повторный поиск проходит.

**Validation:**
- при `403` результат содержит признак ошибки/`403`.
- после возврата `200` повторный `hh_proactive_search` → без `error`.

**Статус:** ✅ mandatory

---

## CI-сценарий (replay): план моков

Мокаем ровно **два** рубежа — LLM и внешнюю сеть (HH). Всё между ними (MCP-сервер,
registry, transport, снапшот-стор, генератор HTML) работает по-настоящему.

| Что мокаем | Чем | Что проверяем вместо реального |
|---|---|---|
| LLM (фразы + скоринг + сообщения) | `tests/support/llm-provider-fixture.cjs` (Nock, записанные ответы) | состав/порядок LLM-вызовов, попадание ответа в результат |
| HH API (внешняя сеть) | `tests/helpers/mock-hh-server.js` (loopback HTTP) + `tests/support/hh-fixture.cjs` | запросы, обработка данных, `403`/восстановление |
| Время/фон | фикстуры не зависят от wall-clock | recall без повторного поиска |

Запуск: `node scripts/staging/run.mjs` (гейт `staging-gate`), под
`scripts/staging/isolation-guard.cjs`. LLM-судья сюда **не** допускается: в CI
«судья» — зафиксированный ответ фикстуры.

Реализации: `scenarios/cold-search-replay/replay.test.cjs` (node, без браузера) и
`tests/staging/cold-search.spec.cjs` (Chromium, тот же flow + UI-инварианты).

## Edge cases

| Ситуация | Ожидаемое поведение |
|---|---|
| Нет активной вакансии | `hh_funnel_stats`/`hh_proactive_view` возвращают просьбу выбрать вакансию, без падения |
| HH отвечает `403` на поиск | ошибка доступа, не нулевой результат; страница ревью остаётся доступной |
| Провайдер перезапущен | recall из снапшота, без нового обращения к HH |
| Пустой результат поиска | страница ревью с пустым состоянием, без выдуманных кандидатов |
| Текст с мультизначными фильтрами | повторяющиеся query-параметры, не запятая |

---

## Проверяемые инварианты

1. **Один вызов `hh_proactive_search` = полный цикл** (фразы → поиск → скоринг →
   снапшот → URL), без ручных промежуточных шагов.
2. **Recall не переспрашивает HH** — снапшот durable, переживает рестарт.
3. **Платная база не задействуется** на поиске/скоринге — только на явном
   приглашении (см. контракт политик `provider-manifest.json`).
4. **Ошибка доступа не маскируется под пустой результат.**
5. **CI — детерминированный replay**; живой LLM/сеть — только staging.

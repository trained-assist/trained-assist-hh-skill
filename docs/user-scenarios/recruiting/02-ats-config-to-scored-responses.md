# Recruiting — ATS-конфиг вакансии до скоринга откликов

**Домен:** HR / рекрутинг (HeadHunter)
**Класс:** exploratory (вне детерминированного гейта; на staging может
оцениваться LLM-судьёй)
**Тулы:** `hh_extract_ats_config`, `hh_evaluate_candidate`, `hh_batch_evaluate`,
`hh_generate_message_to_applicant`, `hh_get_messages`, `hh_send_message`
**Охват:** от текста вакансии до оценки кандидатов и черновика ответа (отправка —
только после подтверждения).

---

## Контекст (начальный state)

- Профиль подключён к HH, активная вакансия выбрана.
- Есть новые отклики (`/negotiations/response`) с полными резюме.
- ATS-конфиг ещё не извлечён.

---

## Сценарий

### Шаг 1 — Извлечение ATS-конфига

```
User: настрой критерии подбора под эту вакансию
```

**Ожидаем:** `hh_extract_ats_config({ vacancy_text })` через LLM формирует
required / preferred / thresholds и сохраняет конфиг для вакансии. Нокаут-критериев
в генерируемом конфиге нет: жёсткие условия выражаются весом в `required` и фильтрами.

**Validation:**
- результат `ok=true`, `config` содержит непустые `required`/`preferred` и
  `pass_threshold` в диапазоне 0–10;
- конфиг нормализуется (старые схемы `required_skills`/`thresholds` не роняют
  скоринг);
- **критерии измеримы**: `hh-criteria-guard` чистит черновик — неизмеримый критерий
  заменяется измеримой формулировкой, а если замены нет, удаляется; тул возвращает
  `replaced_criteria` и `dropped_criteria`;
- `knockout` в сохранённом конфиге отсутствует, если рекрутер его не заводил вручную
  (легаси из старых конфигов читается как раньше).

**Статус:** 🔵 exploratory (CI: `tests/behavior/tools.test.cjs`)

---

### Шаг 2 — Оценка кандидата

```
User: оцени отклики по критериям
```

**Ожидаем:** `hh_evaluate_candidate` считает балл по рубрике и возвращает
`verdict` (ПРОПУСТИТЬ / УТОЧНИТЬ / ОТКЛОНИТЬ) с evidence.

**Validation:**
- результат содержит числовой `score` и `verdict`;
- провал нокаут-критерия → `score=0`, `verdict=ОТКЛОНИТЬ`, `gaps` заполнены;
- оценка без полного резюме не выдумывается (явная ошибка).

**Статус:** 🔵 exploratory

---

### Шаг 3 — Батч-оценка и сообщение

**Ожидаем:** `hh_batch_evaluate` формирует страницу ревью, `hh_generate_message_to_applicant`
готовит черновик ответа; отправка — только явным `hh_send_message` (политика
`external_message`, требует подтверждения).

Черновик строится в два разных шага (`src/hh-funnel.js`):
1. **что делать** — дешёвый вызов LLM по полной переписке возвращает одно действие из
   закрытого набора: `ask_skills`, `clarify_answer`, `confirm_conditions`,
   `propose_test`, `send_test`, `invite_call`, `followup`, `reject`, `wait`;
   до вызова идут детерминированные правила (последнее сообщение наше → `wait`,
   скор ниже порога → `reject`, тестовое уже сдано → `invite_call`);
2. **как написать** — второй вызов пишет текст под выбранное действие и не решает
   состояние заново.

**Validation:**
- `hh_generate_message_to_applicant` не отправляет ничего сам;
- `hh_send_message` — approval-gated (см. `provider-manifest.json`);
- действие `wait` или `reject` **не порождает** письма (второе письмо в пустоту — был
  живой дефект, #66/#70);
- `send_test` отдаёт текст `test_task` из конфига дословно, без участия модели.

**Статус:** 🔵 exploratory

## План моков

### CI (детерминированный replay)

| Что мокаем | Чем |
|---|---|
| LLM (ATS-конфиг, рубрика, сообщения) | `tests/support/llm-provider-fixture.cjs` (записанные ответы) |
| HH API | `tests/helpers/mock-hh-server.js` (loopback HTTP) |

CI проверяет контракт тулов (envelope, схемы, обработку ошибок) через
`tests/behavior/tools.test.cjs`; качество ATS-разбора LLM-судья в CI не оценивает.

### Staging (живой прогон + LLM-судья) — целевая модель, в этом репо ещё не реализована

Целевая модель (см. `docs/requirements-log.md`, «планируется»): на staging источник
монтируется к sandbox-профилю **настоящим** control plane
(`MCP_SKILL_SOURCES_CONFIG`, per-source `profiles`), поднимается живой Hermes; LLM
вызывается по-настоящему. Cheap-LLM судья оценивает: релевантность извлечённых
критериев, обоснованность вердикта (evidence ссылается на резюме), отсутствие
галлюцинаций и дискриминационных критериев. Судья — только staging, не CI.

## Edge cases

| Ситуация | Ожидаемое поведение |
|---|---|
| ATS-конфиг пуст после нормализации | явная ошибка «пересохрани конфиг», не тихое «все 0» |
| Резюме не открыто (restricted) | явная ошибка, не выдуманная оценка |
| LLM вернул не-JSON | ошибка шага, безопасный ретрай по бюджету |
| `hh_send_message` без подтверждения | политика core не даёт отправить |

---

## Проверяемые инварианты

1. **Скоринг детерминирован по конфигу** — балл считается кодом, не «на глаз» LLM.
2. **Оценка опирается на полное резюме**; иначе явная ошибка.
3. **Чтение ≠ отправка**: оценка/черновик не авторизуют внешнее сообщение.
4. **CI — replay фикстур**; живой LLM и судья — только staging.
5. **Критерий измерим** — качество критерия проверяется запуском, а не только
   инструкцией в промпте (иначе каждая регенерация возвращает тот же шум).
6. **Решение и написание — разные шаги** — состояние воронки не выводится заново из
   прозы на каждом письме.
7. **Молчание — допустимый исход** — «ничего не делать» это полноценное действие.
